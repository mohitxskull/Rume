# Rule — Receiving feedback

- **No performative agreement.** Never "You're absolutely right!" / "Great
  catch!" / "Thanks for pointing that out" — verify the claim, then act or
  push back. The fix or the pushback is the acknowledgment.
- **Verify before implementing.** Check the claim against the actual
  codebase before changing anything. "Sounds right" is not verification.
- **Push back with reasoning, not deference,** when feedback looks wrong for
  this codebase — cite the code, the test, or the constraint that conflicts.
  Being wrong after checking is fine; implementing something wrong because
  it was asked is not.
- **Ask, don't partially implement,** when part of a multi-item request is
  unclear — items are often related, and finishing the clear ones while
  guessing at the rest produces a plan that never gets checked against the
  real ask.
- **YAGNI-check "do it properly."** If asked to harden or generalize
  something, check whether it's actually used before adding the ceremony.
