# Jobs & Worker Concurrency Review — v04

## Summary

The core PostgreSQL job path is sound and now verifiable end-to-end: lease-token fencing with `rows_affected()` assertions, database-clock authority (`clock_timestamp()`) across claim/renew/ack/nack/dead_letter, panic isolation wrapped around the *polled* future, soft-completed retention preserving the partial unique index, and tenant-namespaced idempotency keys. All 12 jobs-related container tests pass (`cargo test -p rume --all-features --test containers -- jobs:: job_reliability::` → `12 passed; 0 failed`). Two major defects remain: (1) commit `a59bab0` silently re-added idempotency-lock release on the retryable path, reversing the settled v03 M2 remediation with no rationale comment, and (2) the Redis worker-heartbeat registry — the abandoned-worker recovery authority — computes expiry from the host clock instead of Redis server-side time. Neither is a data-corruption defect at current call sites, but both undermine the duplicate-execution defenses the subsystem was built around. **Not ready to ship as-is; the PostgreSQL fencing core is ready, the Redis reliability path is not.**

Scope note: PostgreSQL and Redis are the only supported job backends; MySQL/SQLite parity was not assessed and is not required.

## Findings

### M1 Settled retry-idempotency decision reversed without rationale: retryable failures release the idempotency lock

- **Where:** `rume/src/jobs/worker.rs:547-559` (re-added in commit `a59bab0`); interacting code: `rume/src/jobs/redis.rs:347-394` (release Lua), `rume/src/persistence/sql/postgres/jobs_schema.sql:17-26`
- **What it says:**
  ```rust
  if let Some(backoff) = job.retry_policy.next_backoff(job.attempt) {
      if let (Some(store), Some(key)) = (&idempotency_store, &effective_key)
          && let Err(rel_err) = store.release_with_token(key, &token).await
  ```
  and the release Lua script (`redis.rs:361-382`) additionally deletes any `COMPLETED` record unconditionally (`string.sub(current, 1, 9) == 'COMPLETED'` — no token check) and, for empty tokens, any `IN_PROGRESS:<anything>`.
- **Why it's a problem:** This is the exact shape v03 M2 removed and v03/diff/v01 verified fixed: the lock is released *while the job is waiting for its retry backoff*, leaving the idempotency key unowned during precisely the window the finding targeted. `a59bab0` reinstated it with only incidental error logging and **no `Why:` comment** — the decision is silent, contrary to `.opencode/rules/70-code-rationale.md`, and contradicts the settled review outcome. Consequence, honestly scoped: the PostgreSQL partial unique index (`jobs_schema.sql:26`, status `NOT IN ('dead_letter','purged')`) prevents a duplicate *enqueue* while the original job is `pending`/`in_flight`, so webhook-style producers that re-enqueue cannot create a second job row; the released lock is not load-bearing for that path. The defect is real for (a) any same-key caller that uses the exported `RedisIdempotencyStore` as its guard without going through Postgres enqueue (check-then-act side effects, e.g. a webhook handler that charges before enqueuing a follow-up job), and (b) the `release` invocation itself, which can erase a `COMPLETED` record it did not write, destroying the 24h cached-result dedup every subsequent duplicate relies on. Root cause: same missing rule as v03 M2 — the idempotency lock's lifetime is not tied to the job's terminal states (DLQ / success), and lock release was treated as generic cleanup rather than an ownership transfer.
- **Suggested fix:** Remove `release_with_token` from the retryable branch (`worker.rs:550-559`); release only at terminal transitions (fatal/unknown/serialization → DLQ, and retries-exhausted → DLQ, both already present at `worker.rs:524-546, 570-584`). Delete the `string.sub(current, 1, 9) == 'COMPLETED'` arm from the release Lua script or gate it on the same token check. If the reversal was intentional (e.g. to avoid 300s lock residency for permanently-failing-then-abandoned keys), record it as a `Why:` comment at the call site and re-open v03 M2 explicitly in the ledger — do not smuggle it into an unrelated lease commit.
- **Evidence:** Static verification (file:line cited above; `git show a59bab0` confirms the release call was added in that commit; `git show 1a3cf5f:rume/src/jobs/worker.rs` confirms it was absent after the v03/diff fix). Not executed as a failing test: no test covers "release-on-retry window" — the existing suite passes with either behavior; the defect is a contract reversal, not a failing assertion.

### M2 Redis heartbeat registry (abandoned-worker recovery) computes expiry from host time — split-brain across hosts

- **Where:** `rume/src/jobs/redis.rs:13-18` (`current_epoch_millis()`), `:76-77` (`record_heartbeat` scores), `:100-114` (`is_alive` comparison), `:124-145` (`reap_dead_workers` compares `-inf..now`)
- **What it says:**
  ```rust
  let now = current_epoch_millis();               // std::time::SystemTime::now()
  let expires_at = now.saturating_add(ttl.as_millis() as i64);
  redis::cmd("ZADD").arg(&self.set_key).arg(expires_at).arg(&wid)...
  ...
  if let Some(exp) = score { Ok(exp > now) }      // host clock vs peer-written score
  ```
  and `reap_dead_workers` passes the host `now` as the `ZRANGEBYSCORE` upper bound.
- **Why it's a problem:** Every worker writes ZSET scores derived from *its own* host clock, and every reaper/`is_alive` call compares against *its own* host clock. A worker whose clock runs slow (VM suspend/resume, lost NTP sync) writes low scores and is reaped as "dead" by its peers while alive; `reclaim_abandoned_jobs` then resets its `in_flight` PG jobs to `pending` (`postgres.rs:338-352`, `jobs_reap.sql`), a peer re-claims and re-executes them concurrently — duplicate execution of side-effecting jobs, invisible to PostgreSQL fencing, which prevents state corruption but not the double side effect. A fast-clocked worker appears alive indefinitely, silently disabling abandoned-worker recovery for its jobs. This is the same defect class as v03 coordination C1 (client wall-clock skew → split-brain; graded C there), and the v04 charter requires Redis jobs to use Redis server-side time, not host `SystemTime::now()`. The peer-heartbeat path is therefore not a safe authority for "this worker is dead" on mixed-clock fleets. Root cause: lease/liveness time authority is host-side in the Redis reliability path while the PG job path was (correctly) moved to database-clock authority in `a59bab0`/`bd397cd`/`11bbe3a` — the refactor did not extend to Redis.
- **Suggested fix:** Evaluate time in Redis. Minimal shape: store scores with Redis server time (`ZADD key (TIME-derived ms + ttl)` or `SETEX rume:jobs:hb:<worker_id> ttl 1` + `SCAN`, or keep ZSET but compute `now` via the `TIME` command inside a Lua script, as coordination's Redis paths do). Replace `is_alive`/`reap_dead_workers` to compare against the server clock (single round trip, or server-evaluated Lua returning dead IDs). Alternatively, document single-clock (single host / fleet-wide disciplined NTP) as an explicit operational requirement — unacceptable as an implicit default.
- **Evidence:** Static verification (file:line cited; call path `JobWorker::start()` → `record_heartbeat` loop `worker.rs:299-306`; recovery consumed by `reclaim_abandoned_jobs` `worker.rs:308-333`). Executed: `job_reliability::worker_heartbeat_tracking_and_reaping` passes on a single host (clock skew absent) — i.e. the test cannot detect this defect. Not executed under skew: no test injects clock skew; defect class confirmed by reading the comparison sites.

### m1 PostgreSQL `enqueue_delayed` computes `available_at`/`created_at` from host time, then compares against the database clock

- **Where:** `rume/src/jobs/postgres.rs:98-99, 104, 111-112, 118`; comparison site `persistence/sql/postgres/jobs_claim.sql:8-9`; `nack` does the inverse (`postgres.rs:253` uses `clock_timestamp()`)
- **What it says:** `let now = current_epoch_millis();` (host `SystemTime`) then binds `available_at = now + delay` and `created_at = now`; the claim query re-evaluates eligibility as `available_at <= clock_timestamp()`.
- **Why it's a problem:** Cross-clock comparison. A host ahead of the database defers its jobs by the skew; a host behind releases delayed jobs early (e.g. a "send at 09:00" job fires early). `nack` already uses `clock_timestamp()` for `available_at`, so enqueue and retry paths use different time authorities for the same column. Consequence is scheduling error bounded by skew, not corruption — below M grade — but it is the same host-time pattern the `6bd0e39` outbox change eliminated from retry scheduling.
- **Suggested fix:** Compute `available_at` in SQL: bind `delay_ms` and insert `(EXTRACT(EPOCH FROM clock_timestamp()) * 1000)::BIGINT + $n` for both `available_at` and `created_at` (matching `nack`). Keep host time out of all persisted scheduling columns.
- **Evidence:** Static verification (file:line cited; read of `jobs_insert.sql` binding order). Not executed: skew injection not run; magnitude unverifiable here.

### m2 Completed jobs are retained forever — the `purged` status referenced by schema and arbiter is never produced; table and unique index grow without bound

- **Where:** `persistence/sql/postgres/jobs_schema.sql:10, 26`; `jobs_insert.sql:6`; `rume/src/jobs/postgres.rs:128`; grep for any writer of `status = 'purged'` finds **none**
- **What it says:** `idx_rume_jobs_idempotency` covers `status NOT IN ('dead_letter', 'purged')` — i.e. every `completed` row permanently occupies the unique index. The v03 C3 fix requested "a periodic background cleanup sweep to prune completed jobs older than a configurable retention period (e.g. 7 or 30 days)" or a dedicated completions table; only the soft-completion half landed. No retention config, sweep query, or purge job exists anywhere in the tree.
- **Why it's a problem:** In a high-throughput deployment `rume_jobs` (payloads are full job bodies) and its idempotency index grow unboundedly; every duplicate delivery scans an ever-growing index; backup/vacuum cost rises monotonically. It also blocks re-enqueue semantics forever for one-shot keys that later legitimately recur (e.g. monthly invoice `inv-2026-11`). Operability gap, not correctness — below M.
- **Suggested fix:** Add `completed_retention: Duration` to the queue config (default 7–30d), a periodic sweep (`UPDATE rume_jobs SET status = 'purged' WHERE status = 'completed' AND completed_at < clock_timestamp() - retention` — the index already excludes `purged`), or a dedicated `rume_job_completions(idempotency_key, completed_at)` written in the same transaction as completion's `ack()`. Least-scope option: the `purged` UPDATE, since the schema already anticipates the status.
- **Evidence:** Static verification (file:line cited; `grep -rn "'purged'" rume/` → 3 references, all read-side, zero writers). Not executed: no retention path to test.

### m3 Idempotency Lua scripts are fail-open on empty tokens and un-token'd `COMPLETED` — the fence is opt-out

- **Where:** `rume/src/jobs/redis.rs:309-328` (`complete_with_token`), `:361-383` (`release_with_token`), `:205-207, 283-285, 343-345` (legacy unfenced entry points), `rume/src/jobs/worker.rs:399` (`unwrap_or_default()`), `reliability.rs:60-62`
- **What it says:** With `ARGV[3] == ''`/`ARGV[1] == ''` (empty token), `complete_with_token` matches **any** `IN_PROGRESS:*` record (`redis.rs:317-318`) and `release_with_token` deletes **any** `IN_PROGRESS:*` (`redis.rs:370-371`); both additionally match/delete any `COMPLETED` record with **no token check at all** (`redis.rs:317-318, 372-373`). Public `IdempotencyStore::release()`/`complete()` map to the empty-token path. If `job.lease_token` is `None`, the worker silently executes in fully unfenced mode.
- **Why it's a problem:** The fencing the v03 M5 remediation added is bypassed by (a) any caller using the legacy API, and (b) any job without a lease token — a silent degradation, not an error. Empty token should mean "unsupported fencing", not "match everything". Cross-worker lock deletion and forged `COMPLETED` writes become possible without the victim noticing (errors are swallowed to logs by callers, e.g. `worker.rs:528-536`). In-tree production callers pass real tokens (Postgres always sets one), so this is a public-API hazard rather than a live in-tree breach — hence m, not M — but it is a security-relevant fail-open in a crate-root-exported type (`lib.rs:75-79`).
- **Suggested fix:** Fail closed: when the token argument is empty, the Lua scripts must return `0` (no-op) for `IN_PROGRESS:*`/`COMPLETED` records, or the scripts should require `ARGV[x] ~= ''`. Prefer deleting the `COMPLETED` arm from `release` (completion eviction is an explicit administrative operation) and/or adding a separate `purge_completed(key, token)` with explicit semantics. In `worker.rs`, treat `lease_token: None` as an error for idempotency-fenced jobs, not as `""`.
- **Evidence:** Static verification (file:line cited; Lua bodies read in full). Not executed: no test covers empty-token calls; `job_reliability::idempotency_store_lifecycle` exercises only tokenless happy path on a single Redis.

### m4 Non-uniform trait failure semantics: DLQ admin APIs default to silent success; unsupported `renew_lease` is treated as lease loss

- **Where:** `rume/src/jobs/queue.rs:81-95` (`list_dead_letters` → `Ok(vec![])`; `replay_dead_letter` → `Ok(())`), vs `queue.rs:56-73` (`renew_lease` default → `Err(Unsupported)`), vs `rume/src/jobs/worker.rs:465-486` (first heartbeat tick is immediate — `interval.tick().await` at line 467 — and *any* renew error cancels the handler)
- **What it says:** The trait fails closed for renewal but fails open for the DLQ admin APIs ("no dead letters", "replay succeeded" — both Lies for a backend that hasn't implemented them), and the worker treats "renew unsupported" identically to "lease lost": a backend without `renew_lease` (the documented default, e.g. a future in-memory or Redis-only queue) has every cooperative handler cancelled at job start.
- **Why it's a problem:** (1) An operator calling `replay_dead_letter` on a non-implementing backend is told it succeeded; the job stays dead-lettered — silent, unobservable loss of the one job being replayed. (2) `list_dead_letters` returning empty masquerades as a clean DLQ. (3) Backends that legitimately cannot renew (allow-listed default) trigger mass spurious cancellation. Root cause: trait defaults were added ad hoc; two are fail-open, one fail-closed, and the worker does not distinguish `Unsupported` from lease-lost.
- **Suggested fix:** Make `list_dead_letters`/`replay_dead_letter` defaults return `Err(JobError::Unsupported(..))`, mirroring `renew_lease`. In the heartbeat loop, match on the renew error: `Unsupported` → log once and disable the renewal task without cancelling the handler; other errors → current lease-lost path. If cancellation-on-any-error is intended semantics, document it on the default impl.
- **Evidence:** Static verification (file:line cited; read of all four default bodies and the heartbeat loop). Not executed: no non-Postgres `JobQueue` backend exists in-tree to demonstrate the spurious-cancellation path end-to-end.

### m5 Process-killing poison jobs can never reach the DLQ; `jobs_claim` applies no `max_attempts` ceiling

- **Where:** `persistence/sql/postgres/jobs_claim.sql:2-13` (`attempt = attempt + 1` unconditionally on every claim, including expired-claim re-drives); enforcement point is only `RetryPolicy::next_backoff(job.attempt)` after a *returned* `Retryable` error (`retry.rs:63-66`, `worker.rs:549`)
- **What it says:** A job whose handler aborts the process (stack overflow, OOM-kill, `std::process::abort`) is never given the chance to return `Retryable`, so its `attempt` climbs without bound across claim/reclaim cycles; no claim-time guard moves it to DLQ.
- **Why it's a problem:** Narrow but real: a deterministically process-fatal job is re-driven forever, consuming worker capacity on every cycle, with zero DLQ visibility — the failure mode is silent operator blindness, not incorrect state. Ordinary handler panics are already caught (M1/v03 M1) and terminate in DLQ; only process death escapes.
- **Suggested fix:** In `jobs_claim.sql`, exclude claims where `attempt >= max_attempts` from the *re-claim* arm and instead transition them (or report them) to dead_letter, e.g. a `dead_lettered_at`-fencing `UPDATE ... WHERE status = 'in_flight' AND lease_expires_at <= now AND attempt >= max_attempts` in the same statement, or a periodic reaper query mirroring `jobs_reap.sql` for this case. Minimum viable: claim sets `status='dead_letter', dead_letter_reason='max attempts exceeded without handler return (process crash?)'` instead of returning the row.
- **Evidence:** Static verification (file:line cited). Not executed: process-kill scenario not injected (would require aborting the worker process in a container test); defect follows by inspection of the claim SQL.

## Positive notes

Preserve these; they are doing real work:

- **Database-clock authority for the entire PostgreSQL lease lifecycle.** `jobs_claim.sql`, `jobs_reap.sql` (deliberately no clock clause), `ack`, `nack`, `dead_letter`, `renew_lease` all evaluate time via `clock_timestamp()` — never `now()`, never the host. The v04 clock-scope requirement for PG is met; `nack` even re-derives `available_at` from `clock_timestamp()` (`postgres.rs:253`).
- **Lease fencing with row-count assertions.** Every mutation fails closed on `rows_affected() == 0` and returns a structured `Fatal` naming the lost lease — superseded workers cannot corrupt or delete peers' jobs (v03 C1 stays fixed).
- **Panic isolation around the polled future.** `AssertUnwindSafe(fut).catch_unwind().await` routes handler panics to DLQ with token-verified release; proven by the passing container test `worker_panic_does_not_leak_in_flight_count`.
- **Soft-completion preserves dedup.** `ack()` transitions to `completed` (never deletes); the partial unique index keeps `ON CONFLICT DO NOTHING` effective — the v03 C3 invariant holds.
- **Tenant-namespaced idempotency all the way down.** Length-prefixed scoped keys (`reliability.rs:66-68`), `COALESCE(tenant_id, '')` in the unique index, and `jobs_insert`'s matching arbiter — cross-tenant dedup collisions are structurally excluded; verified by `jobs::cross_tenant_job_idempotency_isolation` (passed).
- **Heartbeat-loss propagation, not silence.** Lease loss sets `job_cancelled` (cooperative handlers abort), increments `lost_leases`, and logs with job/token context; `drain()` + `InFlightGuard` make shutdown race-free; poll-error backoff caps at 5s.
- **`InProgress` semantics are honest.** Duplicates are re-queued with 2s backoff rather than stranded; `UnknownJob`/`Serialization`/`Fatal` bypass retries to DLQ; poll errors back off exponentially. PG DLQ replay/list APIs are parameterized, ordered by `dead_lettered_at DESC`, and require `status='dead_letter'`.

## Verdict

**Not ready to proceed/ship as-is.**

The PostgreSQL job path (fencing, lease renewal, claim/reclaim semantics, soft-completed dedup, panic isolation, tenant scoping) is implemented correctly and verified by executed container tests — it is ready. The subsystem is not ready because two defects defeat the duplicate-execution defenses where they matter most: **v04 M1** (retry path releases the idempotency lock, reversing the settled v03 M2 decision with no rationale) and **v04 M2** (Redis heartbeat/recovery authority is host-clock, enabling split-brain reaping of live workers → duplicate execution). Both must land before this subsystem ships; **v04 m1–m5** should be triaged with them (m3 especially — it is the same fence, one line of future misuse away from a breach). No Critical findings; no claim herein exceeds what the cited file:line evidence and the recorded commands show. Once M1 and M2 are fixed and the container suites re-run green, this lens would pass.
