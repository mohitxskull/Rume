## Findings

No Critical findings. The durable outbox path holds its invariants; every defect below is on the in-process delivery path, the saga rollback path, or the framework's stated contract.

### M1 EventBus background dispatch silently swallows listener errors and has no panic isolation — one failing listener erases the rest of the event's delivery with zero trace
- **Where:** `rume/src/events/bus.rs:116–136` (`publish_async`; `let _ = listener(...)` at bus.rs:130), `bus.rs:106–111` (`publish_sync` loop), `bus.rs:34–58` (`subscribe`)
- **What it says:** `publish_async` spawns one task that invokes listeners sequentially; every listener result is discarded (`let _ = listener(Arc::clone(&event_arc)).await;`). A panic inside a listener unwinds the shared task and Tokio drops the un-awaited `JoinHandle` silently — subsequent listeners for that event never run. No `tracing`/`log` call exists anywhere in `src/events/`. `publish_sync` propagates `Err` via `?` but offers no panic isolation either.
- **Why it's a problem:** This is exactly the failure class the project already ruled as unacceptable for the outbox relay (v03 M5 → `catch_unwind` + error log): silent loss of delivery with no operator signal. An in-process event (`user.registered` → audit, email, metrics) where listener #2 panics delivers nothing downstream, leaves no log, and the publisher cannot even learn it happened. The bus is a public API used to decouple modules; silent partial delivery is a data-plane integrity hole, not a style issue.
- **Suggested fix:** Wrap each listener call in `std::panic::AssertUnwindSafe(listener(Arc::clone(&event_arc))).catch_unwind().await`; log failures with `event_type`/`listener_index` via `tracing::error!`; either continue delivering to remaining listeners (recommended, matches relay semantics) or fail-fast *documented*; return/report the failure set (e.g., log + counter) instead of `let _ =`.
- **Evidence:** Static — bus.rs read in full; no `catch_unwind`/`tracing` anywhere in `src/events/` (grep). Executed — `events::asynchronous_event_delivery_unblocks_caller` passes but exercises only the happy path; no test observes a failing/panicking background listener. Not executed — failure-injection for the new path (would need a new test; out of lens's write mandate).

### M2 Saga rollback aborts on the first compensation failure, silently leaving remaining completed steps uncompensated
- **Where:** `rume/src/saga/coordinator.rs:98–114`
- **What it says:**
  ```rust
  for &prev_idx in completed_indices.iter().rev() {
      let prev_step = &self.steps[prev_idx];
      if let Err(comp_err) = prev_step.compensate(&mut ctx).await {
          return SagaReport { /* status: SagaStatus::CompensationFailed { error: err, compensation_error: comp_err } */ };
      }
      compensated_names.push(prev_step.name().to_string());
  }
  ```
  On the first compensation error the function returns: compensations for steps before the failing one are **never attempted**, `SagaStatus::CompensationFailed` carries only that one `compensation_error` (single `SagaError`, coordinator.rs:17–21), and nothing in the report marks the skipped steps (the caller must diff `completed_steps` vs `compensated_steps`).
- **Why it's a problem:** A saga exists precisely to reach a consistent state after partial failure; stopping the rollback midway maximizes inconsistency (payment already refunded partially, inventory still reserved). The `Compensated`/`CompensationFailed` distinction implies rollback completeness but the implementation doesn't deliver it. v02's positive note (`v02/correctness.md:239`) described this short-circuit as observed behaviour, not as a safe design; no test covers the "2nd of 3 compensations fails" path, so the hole shipped unexercised. Compensation is the one place a saga must be *total*, not fail-fast.
- **Suggested fix:** Run **all** remaining compensations regardless of individual failures; collect errors (e.g., `compensation_errors: Vec<SagaError>` or first error plus `skipped_compensations: Vec<String>`); record attempted/failed/skipped explicitly in `SagaReport` (extend `compensated_steps` or add `compensation_failures`); update `SagaStatus::CompensationFailed` accordingly (pre-v1, breaking change acceptable); add an integration test with 3 completed steps where the middle compensation fails — assert the last compensation still ran and both errors are reported.
- **Evidence:** Static — coordinator.rs read in full; `SagaStatus::CompensationFailed` carries a single error (coordinator.rs:17–21). Executed — `saga::test_saga_compensation_failure` passes but only exercises a *single* compensation step, never a multi-step partial rollback; no test asserts whether step 1 is compensated when step 2's compensation fails.

### M3 A panicking saga step unwinds through `Saga::run` — no compensation of completed steps, no `SagaReport`, no error
- **Where:** `rume/src/saga/coordinator.rs:93` (`step.execute(&mut ctx).await`), `rume/src/saga/step.rs:66–72` (`FunctionalStep` passes the closure's future straight through), `rume/src/saga/coordinator.rs:102` (compensations likewise unguarded)
- **What it says:** No `catch_unwind` exists anywhere in `src/saga/`. A panic in an action closure (e.g., `unwrap()` on malformed context, assertion on a broken invariant) propagates out of `Saga::run` to the caller: completed steps are never compensated, the caller gets an unwind instead of a `SagaReport`, and the failure is indistinguishable from a crash. Compensations are equally unguarded — a panicking compensator kills rollback the same way.
- **Why it's a problem:** Identical failure class to the outbox dispatcher panic ruled Major in v03 (M5) and to the jobs-worker panic isolation remediated in 2f747ef — the codebase's settled position is that user closures must not unwind through framework control flow. A saga that charges a card then panics on a JSON assert leaves the charge in place with no refund attempt and no report. v02's positive note praised compensation ordering, but ordering is irrelevant if a panic converts the whole rollback into an unwind.
- **Suggested fix:** Wrap `step.execute` and `step.compensate` in `std::panic::AssertUnwindSafe(fut).catch_unwind().await` (futures-util is already a dependency of relay); map panic to `SagaError::Aborted { saga: self.name, reason }` (or a dedicated `StepPanicked`); route to the same compensation path as an action error; add an integration test where step 2 panics after step 1 committed side effects — assert compensation for step 1 ran and the report is `SagaStatus::Compensated`/`CompensationFailed`, not an unwind.
- **Evidence:** Static — grep for `catch_unwind`/`AssertUnwindSafe` in `src/saga/` returns nothing; coordinator.rs and step.rs read in full. Executed — `saga::*` (3 tests) all pass; none injects a panic. Not executed — panic-injection test not written (reviewer may not modify source).

### M4 The failure window between successful external publication and `mark_published` is tested but un-named: the crate claims "guaranteed, atomic" publication and never states its at-least-once contract or the consumer idempotency requirement
- **Where:** `rume/src/outbox/mod.rs:1` ("Transactional Outbox pattern for guaranteed, atomic event and message publication."); `rume/src/outbox/relay.rs:256–265` (skip-ack on lease loss — correct behaviour, no contract wording); `rume/src/events/mod.rs:1`; consumer-idempotency test `rume/tests/integration/outbox.rs:844–904`; heartbeat-loss test `rume/tests/integration/outbox.rs:1027–1081`
- **What it says:** When dispatch succeeds externally but the lease was lost mid-dispatch (or `mark_published` fails after the side effect), the relay deliberately skips the ack: the message stays `inflight`, is later recovered, and is **re-dispatched**. That redelivery path is executed in tests. Nowhere in the crate's own documentation, changelog, or module docs is this stated as at-least-once semantics; the module doc overclaims ("guaranteed, atomic event and message publication" — nothing external is guaranteed, and the atomicity ends at the DB commit). The consumer contract (idempotency keys, dedup store, or natural idempotency) is absent, and there is no guidance on when to use the bus vs the outbox (see m11).
- **Why it's a problem:** Charter invariant (d) requires the external side effect that cannot commit atomically with the outbox to be *explicitly* at-least-once with the consumer contract carrying an idempotency strategy — this codebase implements the mechanics correctly but never tells the user. A team wiring a payment/webhook consumer against this API will produce duplicate charges exactly in the window the framework silently permits. The v03/diff remediations all closed state-corruption holes; this is the remaining contract hole: the failure window is **named nowhere it can be read**, only in review artifacts.
- **Suggested fix:** Rewrite `outbox/mod.rs` docs: (1) atomicity is limited to the DB transaction; (2) publication is **at-least-once**; (3) name the exact window — success of the dispatcher vs `mark_published` commit/lease validity; (4) state the consumer obligation (idempotent handler or dedup store, pointer to `scoped_idempotency_key` in `rume::jobs::reliability` as the in-repo pattern); (5) name the existing tests as executable proof of the semantics; (6) delete/qualify "guaranteed, atomic". Same wording in `relay.rs` on `new_cancellable`.
- **Evidence:** Static — module docs read; relay.rs skip-ack path read; `grep -ri "at-least-once" rume/src` → 0 hits; `grep -rn "idempoten" docs` → only review/plan artifacts, none user-facing. Executed — the window is *tested*: `test_outbox_relay_heartbeat_failure_during_active_dispatch_propagates_cancellation_and_failed_transition` (dispatch returns Ok, lease lost → `failed_transitions=1`, no ack) and `outbox_relay_failed_transition_is_distinguished_and_drain_fails` (mark_published fails → not published, error surfaced); redelivery after recovery is exercised by `outbox_claim_lease_recovery_of_abandoned_messages`; consumer idempotency by `duplicate_event_delivery_consumer_idempotency_prevents_duplicate_effects`. Not executed — end-to-end duplicate redelivery assertion against a live broker (no broker fixture exists).

### m1 `fetch_pending` executes the locking claim SELECT (`FOR UPDATE SKIP LOCKED`) outside any transaction — a read path that can transiently under-report and takes row locks it never needs
- **Where:** `rume/src/persistence/postgres.rs:325–339`, `rume/src/persistence/mysql.rs:334–348` (both call `OUTBOX_CLAIM_SQL`); `sql/postgres/outbox_claim.sql:8`, `sql/mysql/outbox_claim.sql:3,8` (`FORCE INDEX`, `FOR UPDATE SKIP LOCKED`); `sql/sqlite/outbox_claim.sql` (no lock clause — unaffected)
- **What it says:** `fetch_pending` "fetches up to `limit` pending messages" but issues the exact locking query used for claims: rows locked by concurrent claim transactions are *skipped*, so the read returns a subset; on MySQL it also forces an index. Integration tests use `fetch_pending` as a plain assertion read (`transactional_outbox_*`, `outbox_relay_tracks_failures_and_exhaustion`).
- **Why it's a problem:** A monitoring/assertion read that silently omits rows defeats exactly the verification the test suite performs; in production any operator polling fetch_pending sees phantom "missing" messages under load. Taking locks on a non-transactional read is wasteful and can interfere with the locking readers of peer relays.
- **Suggested fix:** Split the SQL: keep `FOR UPDATE SKIP LOCKED` only in `claim_pending_with_lease`; implement `fetch_pending` with a plain `SELECT … WHERE status='pending' AND (next_retry_at IS NULL OR next_retry_at <= <wall clock>) ORDER BY created_at ASC, id ASC LIMIT …` (no lock, no FORCE INDEX), or document fetch_pending's skip semantics in the trait doc if locking behaviour is truly wanted.
- **Evidence:** Static — both backends read; SQL files read. Executed — `cargo test --features sqlite --test integration -- outbox` passes (sqlite path has no lock clause). Postgres/MySQL read-path identical; differential not executed (containers run pass but no skip-under-lock assertion exists).

### m2 MySQL `claim_pending_with_lease` returns `lease_expires_at: None` while Postgres/SQLite return `Some(<db-clock expiry>)` — cross-backend API inconsistency
- **Where:** `rume/src/persistence/mysql.rs:380–394` (`msg.lease_expires_at = None;`) vs `postgres.rs:363–377` (`RETURNING lease_expires_at`), `sqlite.rs:388–401`
- **What it says:** MySQL performs the `UPDATE … lease_expires_at = UNIX_TIMESTAMP() + ?` without `RETURNING` (MySQL has none) and never re-reads the value; the returned `OutboxMessage` carries `lease_expires_at: None`. Postgres/SQLite populate it via `RETURNING`.
- **Why it's a problem:** Any caller (logging, metrics, drain UIs, tests) reading the claimed message's lease expiry gets `None` only on MySQL; behavior diverges per backend for an identical API call, and the field is silently falsified rather than documented.
- **Suggested fix:** In the same transaction, `SELECT UNIX_TIMESTAMP() + ?` after the UPDATE (same 1s granularity, ≤1s error) or drop the field from MySQL's docs; simplest honest fix is the re-read or explicitly document `lease_expires_at == None` on MySQL in the trait doc (`repository.rs:32–37`).
- **Evidence:** Static — mysql.rs:392 read; postgres/sqlite `RETURNING` paths read. Executed — `test_mysql_outbox_claims_skip_locked_and_lease` passes; it does not assert the returned `lease_expires_at`.

### m3 `mark_failed` still computes `retry_count` in Rust and writes the absolute value — the last non-atomic read-modify-write in the lease lifecycle
- **Where:** `rume/src/persistence/postgres.rs:456–484`, `mysql.rs:472–506`, `sqlite.rs:481–510`
- **What it says:** `SELECT retry_count …` → `retry_count = row + 1` in Rust → `UPDATE … retry_count = $2`. Both statements carry the fence predicate, so inter-worker races error out — but two same-token calls (a retried dispatch path, or a future caller) lose the increment, and the UPDATE is not conditional on the count read.
- **Why it's a problem:** The v03 M3 fix relied on fencing, which is correct for the relay's today usage; it did not make the increment atomic, which was the originally suggested shape. Defense-in-depth against the one remaining race is free: it is also what keeps the DLQ threshold honest if the call graph ever widens.
- **Suggested fix:** Single fenced statement: `UPDATE rume_outbox SET retry_count = retry_count + 1, status = CASE WHEN retry_count + 1 >= $1 THEN 'failed' ELSE 'pending' END, next_retry_at = <wall clock> + $2, … WHERE id = $3 AND lease_token = $4 AND status='inflight' AND lease_expires_at > <wall clock>` (one round-trip, no SELECT); or keep the SELECT but write `retry_count = retry_count + 1` and derive status in SQL `CASE`.
- **Evidence:** Static — all three backends read; no test covers same-token double `mark_failed`. Executed — outbox suites pass; none exercise the race.

### m4 Backoff computation `2u64.pow(retry_count.saturating_sub(1) as u32)` overflows for large `max_retries`
- **Where:** `rume/src/persistence/postgres.rs:471`, `mysql.rs:487`; `sqlite.rs:496`; relay passes user-configurable `OutboxRelayConfig::max_retries` (`relay.rs:81,97–101`)
- **What it says:** `2u64.pow(n)` panics in debug builds (overflow) for `n ≥ 64`; a user setting `max_retries = 100` makes `mark_failed` panic at the 64th retry instead of dead-lettering. In release builds it wraps, producing a bogus `next_retry_at`.
- **Why it's a problem:** Configurable retry limits (the v03/diff remediation for hardcoded 5) introduce a new input domain the math never handled; the failure mode is a panic on the failure path — the worst place for one.
- **Suggested fix:** `1u64.checked_shl(n.min(63))` or `2u64.checked_pow(n.min(63)).unwrap_or(u64::MAX)` and/or clamp `next_retry_at` growth; cap effective exponent, not just the counter.
- **Evidence:** Static — pow call sites read. Not executed — no test with `max_retries > 63` exists.

### m5 Trait default `mark_failed_with_max_retries` is mutually recursive with `mark_failed` — an implementer trap that stack-overflows at runtime
- **Where:** `rume/src/outbox/repository.rs:64–82` (`mark_failed` → `mark_failed_with_max_retries(…, 5)`; default `mark_failed_with_max_retries` → `self.mark_failed(…)`)
- **What it says:** A backend implementing the required `mark_failed` by delegating to `self.mark_failed_with_max_retries(...)` (exactly the idiom used by postgres/mysql/sqlite) but not overriding the `mark_failed_with_max_retries` default, recurses forever: default → `mark_failed` → default → … Inconsistent with `renew_outbox_lease`/DLQ defaults, which return `OutboxError::Unsupported` with an explanatory message.
- **Why it's a problem:** The failure mode is a runtime stack overflow on first use — not a compile error, not a clean `Unsupported`. All in-tree backends override both methods, and `DatabasePool` delegates (`pool.rs:441–458`), so nothing breaks today; the trap only bites the next `OutboxRepository` implementor, which for a framework crate is the expected audience.
- **Suggested fix:** Make the default `mark_failed_with_max_retries` return `Err(OutboxError::Unsupported("outbox max-retries marking not supported by this repository backend (id={…})"))` (same pattern and comment style as `renew_outbox_lease`), or remove the defaults and require both methods; a comment should state why.
- **Evidence:** Static — repository.rs read; postgres.rs:442–444 and mysql.rs:458–460 confirm the delegation idiom the trap requires. Executed — `test_outbox_repository_unsupported_renewal_default_returns_error` passes for the renewal default; no equivalent test exists for the recursion pair.

### m6 `recover_expired_claims(max_lease_age_secs)` ignores its argument in all three backends — dead parameter, misleading trait docs
- **Where:** `rume/src/outbox/repository.rs:84–92` (trait doc still says "whose claim lease has expired"; parameter silently ignored), `sqlite.rs:523` (`_max_lease_age_secs`), `postgres.rs:496–505`, `mysql.rs:512–520`; relay passes `self.config.lease_duration_secs` pointlessly (`relay.rs:171–173`)
- **What it says:** The message-age parameter survived the v03 C2 fix as a no-op: backends execute `OUTBOX_RECOVER_SQL` (wall-clock only) and discard the argument; the relay forwards an unrelated knob.
- **Why it's a problem:** A parameter that looks load-bearing invites future misuse (someone may "restore" age-based recovery or assume it tunes anything), and the docs misdescribe the function's contract.
- **Suggested fix:** Pre-v1 breaking change: remove the parameter (`recover_expired_claims(&self)`) and fix the trait doc; or minimally rename to `_max_lease_age_secs` with a `Why:` comment that expiry is DB-clock authority and age-based recovery was removed (v03 C2). Update relay call site.
- **Evidence:** Static — all backends + trait + relay read. Executed — outbox recovery tests pass and call with arbitrary values (`recover_expired_claims(30)`, `(0)`), confirming the parameter is inert.

### m7 No retention/purge for outbox rows — `published` and `failed` accumulate forever; the DLQ can be inspected and reprocessed but never purged
- **Where:** `rume/src/outbox/repository.rs` (no prune/purge method), `postgres.rs` / `mysql.rs` / `sqlite.rs` (no DELETE path), `relay.rs` (drain only publishes)
- **What it says:** `OutboxRepository` offers `failed_count`/`fetch_failed`/`reprocess_failed` and counts, but no way to delete rows. Every published message row persists indefinitely; `rume_outbox` grows without bound on a busy system, and a false-positive poison pill in the DLQ can never be discarded without SQL access.
- **Why it's a problem:** DLQ "operability" (charter item 7) is incomplete without a purge path: operators are left with manual `DELETE` against a framework-owned table, or unbounded bloat; index maintenance suffers as the table grows (the `(status, created_at)` partial index helps but every `SELECT COUNT(*)` still scans the published tail in MySQL/SQLite without partial indexes).
- **Suggested fix:** Add `purge_published(older_than: Duration) -> Result<usize>` and `purge_failed(id)` (or `purge_failed(ids: &[String])`) to the trait + backends + `DatabasePool`; alternatively document retention as a deployment concern and ship the purge as a CLI/migration — but an API is cleaner pre-v1. Add the same for `pending` is neither needed nor wanted.
- **Evidence:** Static — trait and all backends read; grep `DELETE FROM rume_outbox` → 0 hits. Executed — not applicable.

### m8 SQLite claim has no row-lock semantics — correctness rests on transaction snapshot aborts, and no multi-connection test exercises it
- **Where:** `rume/src/persistence/sql/sqlite/outbox_claim.sql:7` (LIMIT only; no `FOR UPDATE SKIP LOCKED`), `rume/src/persistence/sqlite.rs:372–411` (deferred transaction), `sqlite.rs:49–53` (in-memory pool forced to `max_connections(1)`), `sqlite.rs:75–84` (file DB uses WAL + 5000ms busy_timeout)
- **What it says:** Two concurrent claim transactions can read the same pending rows; the loser aborts with `SQLITE_BUSY_SNAPSHOT` on its first conflicting write, rolling back the whole claim (no corruption — disjoint sets never both commit), but every contending claim fails wholesale. The in-memory test harness serializes all queries on one connection, so `concurrent_relays_claim_disjoint_batches` proves nothing about real file-backed concurrency; file-backed multi-relay SQLite will see recurring claim errors under load instead of clean batches.
- **Why it's a problem:** Silent-failure-free but throughput-hostile: claim contention is indistinguishable (in the relay logs) from other transient DB errors, and the "disjoint batches" guarantee users extrapolate from the sqlite tests does not hold as written.
- **Suggested fix:** Open the claim transaction with `BEGIN IMMEDIATE` (SQLx: `SqliteConnectOptions::transaction_mode(SqliteTransactionMode::Immediate)` for file-backed pools) so writers serialize on the write lock with a bounded busy_timeout instead of snapshot-abort; document that SQLite outbox is single-writer/best-effort for multi-relay; add a file-backed two-connection contention test (tempdir) asserting no duplicate claims (may be flaky-prone — use barriers).
- **Evidence:** Static — SQL, pool configs read. Executed — outbox integration suite passes on in-memory single-connection SQLite; file-backed contention not executed (no such test exists).

### m9 Lock-poisoning is silently swallowed in `subscribe` / `listener_count` / `publish_async` — subscriptions and notifications vanish without error
- **Where:** `rume/src/events/bus.rs:55–57` (`if let Ok(mut subs)` — poisoned lock drops the registration), `bus.rs:83–89` (returns 0), `bus.rs:117–123` (returns empty listeners → `count = 0`, spawn skipped, caller told 0 notified)
- **What it says:** Every read-side use of the `RwLock` uses `if let Ok(...)`/`.map(|s| s.len())` and degrades to silence on poison; only `publish_sync` maps poison to `EventError::Bus`. A panic while a writer holds the lock (e.g., inside `push` — allocation failure aside) permanently amputates the bus for the rest of the process with no signal.
- **Why it's a problem:** Silent data-path degradation violates the fail-visible principle applied everywhere else in the crate after v03 (drain fail-closed, relay error propagation); a `subscribe` call that registered nothing is indistinguishable from one that registered fine.
- **Suggested fix:** Replace silent arms with `tracing::error!` + explicit fallback (or, better, `map_err` → `EventError::Bus` and return `Result` from `subscribe`/`publish_async`; pre-v1 API break is acceptable); never return "0 listeners" for a poisoned bus without logging it.
- **Evidence:** Static — bus.rs read in full. Executed — not applicable (poison injection not implemented).

### m10 `publish_sync` fails fast on the first listener error and never runs the rest; semantics undocumented and untested
- **Where:** `rume/src/events/bus.rs:94–111` (sequential loop, `listener(...).await?`), interplay with M1
- **What it says:** On listener N's `Err`, listeners N+1.. are skipped; the caller receives `EventError::ListenerError` with no indication of which listeners ran or which were skipped; nothing is logged; no panic isolation (a panicking listener unwinds into the caller). Whether fail-fast, continue-and-collect, or retry is *intended* is not stated anywhere.
- **Why it's a problem:** Callers cannot build correct recovery (retry the event? compensate?) without knowing the delivery state; partial delivery with no trace is the synchronous mirror of M1 and equally undocumented.
- **Suggested fix:** Document the semantics in `publish_sync`'s doc comment; either (a) keep fail-fast and say so (at minimum log how many listeners ran before the error), or (b) continue on error and return `Vec<EventError>`/aggregate; add a test with two listeners where the first fails and assert the second's fate matches the documented contract; add panic isolation per listener per M1's fix if unwinding into callers is not intended.
- **Evidence:** Static — bus.rs:94–111 read; doc comment at 91–93 says only "If any listener fails, returns EventError". Executed — `synchronous_dispatch_propagates_listener_error` passes; asserts error text, never asserts listener #2's invocation.

### m11 Dual delivery is possible and undocumented — the same domain event can go out in-process (bus) and externally (outbox → broker) with no framework guidance
- **Where:** `rume/src/events/mod.rs:1`, `rume/src/outbox/mod.rs:1`, intended bridge pattern visible only in `rume/tests/containers/postgres.rs:399–453` (relay → `publish_sync`)
- **What it says:** Nothing in the public API or docs tells a user which path to pick per event, or that both paths together produce duplicate effects (in-process listeners run *and* react to the broker redelivery, and both run again on every outbox redelivery). The test-suite pipeline (relay → `publish_sync`) is the de-facto documented pattern, existing only in a container test.
- **Why it's a problem:** For a framework whose pitch is reliability, two overlapping delivery semantics with no selection rule invites double-charge/double-email architectures; the review found no doc, comment, or lint preventing it.
- **Suggested fix:** Add a short "Delivery paths" section to both module docs: in-process bus = ephemeral, sync/background, at-most-once per listener, no redelivery; outbox = durable, at-least-once, requires idempotent consumers; choose per event; if bridging (relay → bus), consumers must be idempotent (cite M4). One paragraph each is enough.
- **Evidence:** Static — module docs read; only usage pattern found is the container test cited. Executed — `test_postgres_outbox_relay_pipeline_with_event_bus` passes (relay→bus bridge works).

### m12 `created_at` is host-generated whole seconds — cross-node FIFO ordering is approximate under host clock skew
- **Where:** `rume/src/outbox/message.rs:11–16,66,88` (`current_timestamp`, `as_secs()`); ordering relies on it (`sql/*/outbox_claim.sql:6`)
- **What it says:** `created_at` is wall-clock seconds *of whichever host created the row*; lease/retry math is DB-clock (correct), but queue order is not: two relay nodes ingesting concurrently can interleave rows whose host clocks disagree, and intra-second ties fall back to random-UUID `id ASC` (deterministic, not causal).
- **Why it's a problem:** "FIFO event dispatch" claims (v03 M1/m3) hold per-database storage order, not across nodes with skewed clocks; any consumer relying on global event order gets approximate ordering with no documentation of the bound.
- **Suggested fix:** Either source `created_at` from the DB (`DEFAULT (CAST(strftime('%s','now') AS INTEGER))` / `UNIX_TIMESTAMP()` / `EXTRACT(EPOCH FROM clock_timestamp())`) for a single monotonic source, or document "approximate global order; per-producer order only; ties broken by id". Note in docs that ordering across failure/re-enqueue is not causal either.
- **Evidence:** Static — message.rs and claim SQL read. Not executed.

### m13 `pending_count` doc says "currently pending" but counts pending **and** inflight
- **Where:** `rume/src/outbox/repository.rs:94–95`; implementations `postgres.rs:507–518`, `mysql.rs:525–538`, `sqlite.rs:534–547`; used by `try_drain` (`relay.rs:376–379`)
- **What it says:** `SELECT COUNT(*) … WHERE status = 'pending' OR status = 'inflight'` backs a method documented as "Returns the number of currently pending outbox messages."
- **Why it's a problem:** The doc/impl mismatch matters precisely where it's used: drain logic depends on the inclusive semantics; any other caller (metrics, dashboards) reading the doc will under-count and declare drains complete early.
- **Suggested fix:** Rename the doc: "number of unpublished messages (pending + inflight)"; or split into `pending_count()` and `inflight_count()` if finer granularity is needed by metrics; align MySQL/SQLite docs identically.
- **Evidence:** Static — trait + three implementations read. Executed — `outbox_relay_graceful_drain_on_shutdown` passes (relies on inclusive semantics).

## Positive notes

- **DB-clock authority across the entire lease lifecycle** — claim (`outbox_claim.sql:5`), renew/completion/failure/recovery (`renew_outbox_lease`, `mark_published`, `mark_failed`, `outbox_recover.sql:6` — all `FLOOR(EXTRACT(EPOCH FROM clock_timestamp()))::BIGINT` / `UNIX_TIMESTAMP()` / `CAST(strftime('%s','now') AS INTEGER)`). No host time participates in any lease or retry decision anymore; `now()` is absent from the outbox SQL tree. This is the correct foundation and must survive future refactors.
- **Strict lease fencing with `rows_affected` assertion on every mutation** (`postgres.rs:410,433,486,597`, `mysql.rs:426,449,502,613`, `sqlite.rs:435,458,511,622`) — superseded relays cannot complete, fail, renew, or reprocess; verified by `outbox_superseded_worker_cannot_mark_published_or_failed` and `outbox_lease_expiry_rejects_completion_before_another_claims` (both reject even before another worker reclaims), plus live postgres/mysql container fencing tests.
- **Heartbeat + active cancellation done right** (`relay.rs:191–265`) — pre-dispatch renewal, per-message heartbeat task, `Arc<AtomicBool>` cancel signal for dispatchers, skip-ack on lease loss so state is never corrupted by a stale owner; the dispatcher observed-cancellation path is executed by `test_outbox_relay_heartbeat_failure_during_active_dispatch_propagates_cancellation_and_failed_transition`.
- **Failure window contained without corrupting state** — lease loss mid-dispatch ⇒ no ack ⇒ recovery ⇒ redelivery. At-least-once is the right bar, and the code meets it; the only gap is that the contract is unwritten (M4).
- **Panic isolation in the relay via `catch_unwind` on the awaited future** (`relay.rs:241–251`) — the v03/diff defective remediation was correctly rebuilt; dispatcher panic ⇒ `mark_failed` with error context, retry scheduled, lease cleared, relay survives (`outbox_relay_recovers_from_async_dispatcher_panic`).
- **Transactional `save_tx` atomicity, verified not assumed** — commit commits both (`transactional_outbox_commits_atomically_with_business_mutation`; containers `test_postgres_outbox_transactional_outbox_atomicity`, `test_mysql_transactional_outbox_atomicity`); rollback rolls back both (`transactional_outbox_rolls_back_atomically_on_transaction_failure`).
- **Immutable inserts** — `DO NOTHING` everywhere; idempotent retries cannot resurrect published/inflight rows (`outbox_duplicate_insert_preserves_published_and_inflight_state`).
- **Recovery strictly on lease expiry** — message-age revocation is gone; `idx_rume_outbox_lease` (partial in PG) covers the poll; `lease_expires_at IS NULL` is explicitly recovered.
- **Fail-closed drain and visible failures** — `RelayPollResult::is_success`, `try_drain` returns `Err` on any failed transition/repository error, and `start_*` logs them; operators can tell "stuck" from "done".
- **Crash safety of in-flight dispatch** — shutdown/abort mid-dispatch drops the dispatcher and heartbeat; the lease expires and recovery re-queues the message; no partial commit, no stranded claims (validated by the recovery tests and the lease-loss skip-ack path).
- **Saga structure is sound where it matters** — strict reverse-order compensation of completed steps, `CompensationFailed` is a distinct, typed status, context is returned to the caller for inspection, and all three saga paths are executed (`saga::test_saga_*`). Fix M2/M3 rather than rip out the design.
- **Typed event bus core** — TypeId-keyed registry, exact downcasts (cannot fail in-process), handler trait ergonomics clean (`EventHandler`/`subscribe_fn`), and sync dispatch propagates listener errors to the caller by design.

## Verdict

**No — this subject is not ready to proceed/ship without a fix pass.** The outbox core (fencing, recovery, atomic transactions, backoff, DLQ APIs, drain) is production-sound and re-verified by execution on sqlite, live PostgreSQL, and live MySQL; it would satisfy its slice. What is not ready is the rest of this lens's subject: the event bus (M1 — silent background loss, no panic isolation), the saga (M2 — partial rollback abandons remaining compensations; M3 — a step panic skips compensation and destroys the report), and the framework's missing at-least-once contract (M4). Until M1–M4 land with tests (panic-injection for M1/M3; multi-step compensation-failure for M2; doc + pointer tests for M4), do not rely on in-process event delivery or saga rollback for side-effecting work, and do not ship the outbox to users without the consumer-idempotency contract written down. The 13 minor findings are polish on the same theme: visibility (locking read m1, poisoned locks m9, doc/impl drift m13), cross-backend coherence (m2, m5, m8), and arithmetic/API edges (m3, m4, m6, m7, m12). No prior finding regressed; no prior disposition is overturned except the spirit of v02's saga positive note, engaged honestly under M2.
